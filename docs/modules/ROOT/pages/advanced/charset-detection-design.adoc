= Charset Detection Pipeline
:toc:
:toc-placement: left

A hashed byte n-gram model, structural checks for UTF-8/UTF-32/ISO-2022, and a
script-aware text-quality arbitrator.  The design
decision that shapes everything else: collect candidates from every layer, then
arbitrate by decode quality — not first-detector-wins.

== Pipeline overview

The default `EncodingDetector` chain is assembled via the Java SPI.  All results
are collected into an `EncodingDetectorContext` on the `ParseContext`; when a
`MetaEncodingDetector` (currently `JunkFilterEncodingDetector`) is present,
`CompositeEncodingDetector` switches into collect-all-then-arbitrate mode.

[cols="1,2,1,2", options="header"]
|===
| # | Detector | Module | Role

| 1
| `BOMDetector`
| `tika-core`
| First 4 bytes.  DECLARATIVE result on a UTF-8 / UTF-16 / UTF-32 BOM.
  See <<bom-detector>>.

| 2
| `MetadataCharsetDetector`
| `tika-core`
| `Content-Type` charset parameter and `Content-Encoding` from `Metadata`,
  with WHATWG label normalization.  DECLARATIVE.  See <<metadata-detector>>.

| 3
| `MojibusterEncodingDetector`
| `tika-encoding-detector-mojibuster`
| Structural UTF-32/ISO-2022 detection, UTF-8 grammar gate, HTML stripping,
  then a hashed byte n-gram model that also covers UTF-16 and UTF-32.
  STRUCTURAL for structural hits, STATISTICAL for model predictions.  See
  <<nb-pipeline>>.

| 4
| `HtmlEncodingDetector`
| `tika-encoding-detector-html`
| `<meta charset>` / `<meta http-equiv=Content-Type>` via a fast lenient regex
  matcher, resolved through the curated alias table in
  `TikaHtmlCharsetAliases`.  DECLARATIVE.  `StandardHtmlEncodingDetector` is
  available opt-in for the full spec-strict WHATWG prescan.

| 5
| `JunkFilterEncodingDetector`
| `tika-ml-junkdetect`
| `MetaEncodingDetector`.  Arbitrates across all base-detector candidates with
  a hashed n-gram text model.  See <<junk-filter>>.
|===

=== EncodingResult and ResultType

Detectors return `List<EncodingResult>`.  Each carries:

* `charset` — the detected `java.nio.charset.Charset`.
* `confidence` — 0.0 to 1.0.
* `label` — the detector's internal label, which may be finer than the Java
  charset name.
* `resultType` — `DECLARATIVE`, `STRUCTURAL`, or `STATISTICAL`.

In the default chain JunkFilter arbitrates across all three tiers by decode
quality.  A declared charset is not automatically authoritative, but one whose
decoding is byte-identical to at least one other candidate's wins.  See
<<opting-out-of-arbitration>> for plain first-match-wins.

[[bom-detector]]
== BOMDetector

Reads the first 4 bytes:

[cols="1,1", options="header"]
|===
| Byte sequence | Encoding

| `EF BB BF` | UTF-8
| `FF FE 00 00` | UTF-32-LE
| `00 00 FE FF` | UTF-32-BE
| `FF FE` | UTF-16-LE
| `FE FF` | UTF-16-BE
|===

Returns DECLARATIVE.  The HTML detectors deliberately do not handle BOMs, so
`BOMDetector` is the sole source of BOM evidence; that lets JunkFilter arbitrate
when a BOM and a `<meta charset>` tag disagree.

[[metadata-detector]]
== MetadataCharsetDetector

Reads declarative charset hints from the `Metadata` object before any byte
analysis:

* `Content-Type` charset parameter (e.g. `text/html; charset=windows-1251`)
* `Content-Encoding` (used by `RFC822Parser` and similar MIME-aware parsers)

`ISO-8859-1` and `US-ASCII` are normalized to `windows-1252`, because browsers
and the HTML5 spec treat them as aliases for it in practice.  Returns
DECLARATIVE.

[[nb-pipeline]]
== MojibusterEncodingDetector

Pure-ASCII probes stop early; every other probe collects candidates from the
structural checks and the model, which are then ranked STRUCTURAL first.

=== Pure ASCII and ISO-2022

A probe with no byte ≥ 0x80 and no NUL is first checked for ISO-2022-JP/KR/CN.
These encodings are 7-bit and escape-based (`ESC $ B`, `ESC $ ) C`, SO/SI), so
the pipeline scans for the designation escape and then *verifies* by decoding:
the result must contain real CJK at a near-zero replacement rate, which rejects
a stray `ESC $` in ordinary ASCII.

Otherwise, a *pure-ASCII* probe — one whose only control characters are TAB,
LF, FF, CR and ESC — returns windows-1252 at 0.1 confidence: every
ASCII-compatible charset decodes it identically, so the HTML5-canonical name is
the answer.  Any other C0 control sends the probe to the model, because short
BOM-less UTF-16 Thai, Cyrillic or Indic text looks exactly like that (`0E 2A`,
`04 1F`, `09 15`: no NUL, no high byte).  If the model then names anything
other than UTF-16 or UTF-32, the probe still gets the windows-1252 answer.

=== UTF-32 structural (`WideUnicodeDetector`)

Every 4-byte group is read as a 32-bit codepoint in both BE and LE order and
checked for Unicode validity (0x000000–0x10FFFF, surrogates excluded).  Valid
codepoints occupy ~0.004% of the 32-bit space, so non-UTF-32 bytes almost always
produce an out-of-range value within the first 8 bytes.  A hit is a STRUCTURAL
candidate, so UTF-32 is never reported as UTF-16.

The same pass checks UTF-16 surrogate pairing under each byte order; a model
UTF-16 candidate whose surrogates are broken is dropped.  A pair cut by the end
of the probe is not counted as broken.  These checks see the probe with its BOM.

=== UTF-8 grammar gate (`StructuralEncodingRules.checkUtf8`)

Walks the probe looking for valid UTF-8 lead + continuation sequences:

* `LIKELY_UTF8` — grammar valid and at least one complete multi-byte sequence.
  UTF-8 is emitted as a STRUCTURAL candidate alongside the model's output.
* `NOT_UTF8` — grammar violated.  UTF-8 is filtered out of the model's output
  (a few errors in a long probe are tolerated as corruption).
* `AMBIGUOUS` — no complete multi-byte sequence (pure ASCII, or a truncated lead
  at probe end).  No emission.

=== HTML stripping (content-type aware)

When the probe looks like HTML/XML (explicit content type, or unknown),
`HtmlByteStripper` performs a byte-level state-machine strip so the model sees
content bytes rather than markup:

* **Script / style / comment bodies** are dropped entirely — no natural-language
  signal.
* **Text-bearing attribute values** (`alt`, `title`, `placeholder`,
  `aria-label`, `summary`, `label`) are kept, space-separated.  They carry
  user-visible text in the document's charset and are often the only signal on
  pages with a sparse body — Arabic forums with navigation in `title=...`, CJK
  sites with screen-reader `aria-label=...`.
* **Tag-count backoff** — if stripping yields zero well-formed tags the original
  bytes are used.  The probe was not really HTML; common for plain text with
  stray `<` bytes, or EBCDIC content.

=== Hashed byte n-gram model (`HashedNgramEncodingDetector`)

43 classes: CJK multibyte (Big5-HKSCS, EUC-JP, GB18030, Shift_JIS, x-EUC-TW,
x-windows-949), EBCDIC (IBM420/424 in ltr and rtl forms, IBM500, IBM1047), DOS
OEM (IBM437/850/852/855/866), Cyrillic (KOI8-R, KOI8-U, ISO-8859-5), Windows
single-byte (1250–1258, 874), ISO-8859-2/3/6/7/16, Mac (x-MacRoman,
x-mac-cyrillic), UTF-8, UTF-16LE/BE, UTF-32LE/BE, and `binary`.

Features:

* **Byte n-grams** of order 1–3 that hold at least one byte outside printable
  ASCII, TAB, LF and CR.  Pure-ASCII stretches contribute nothing, which keeps
  long English markup from drowning the few bytes that matter, and lets the
  scorer skip them outright.  Unigrams and bigrams index their rows directly;
  trigrams are hashed into 2^16 rows.
* **Column channels**: the byte at even offsets and the byte at odd offsets over
  the first 512 bytes.  Byte n-grams cannot tell UTF-16LE from UTF-16BE (the
  same pairs in a different phase); the column channels can, without relying on
  NUL bytes, which CJK UTF-16 does not have.

Each channel's int8 embedding rows are mean- and max-pooled, a log count of
non-text bytes is appended, and one ReLU hidden layer produces a raw logit per
class.  The model was trained with decode-equivalent siblings as acceptable
answers for each other, so siblings that decode a probe identically score close
together.

A probe with no non-text byte is not scored.

Long probes stop early.  The windows around the first 4,096 non-text bytes are
always scored; if the top class then leads the runner-up by at least 2 logits,
the rest of the probe adds only the windows around byte values not seen yet (a
sibling charset often differs in a single rare byte, which may appear late).
Otherwise the whole probe is scored.

==== Candidate emission

* At most `DEFAULT_TOP_K` (5) charsets are emitted.  Top-1 gets confidence 1.0;
  a runner-up within `MARGIN_LOGITS` (4.0) of it gets `1 - gap / MARGIN_LOGITS`,
  and anything further away is dropped.  Confidence is a margin, not a softmax,
  which saturates on out-of-distribution input.
* Labels that share a Java charset (`IBM420-ltr` / `-rtl`) are merged and score
  as their best member.
* `binary` is not a charset: when it is the top class nothing is emitted, so the
  pool holds only structural candidates, if any, and otherwise the
  windows-1252 fallback at 0.1 confidence.  JunkFilter treats that as
  abstention and defers to a declaration when there is one.

==== Fallbacks and rewrites

* **Probes under 2 bytes**, or an empty pool → windows-1252 at 0.1 confidence.
  The WHATWG default; the detector never returns an empty result.
* **Latin-sibling rewrite** — if the top candidate is a Western Latin sibling
  (x-MacRoman, IBM850, ISO-8859-15) and the probe has at least as many cased
  letters at high-byte positions under windows-1252, rewrite it to windows-1252.

==== CJK decode-failure veto (`CjkDecodeValidator`)

A legacy multi-byte CJK class (GB18030, Big5-HKSCS, Shift_JIS, EUC-JP,
x-windows-949, x-EUC-TW) picked on Latin/Cyrillic/garbage bytes is
*false-CJK*: those bytes do not validate under the charset, so decoding produces
many malformed/unmappable events, whereas real CJK decodes cleanly.  Each
legacy-CJK candidate is decoded under its vendor superset (`CharsetSupersets`)
and its `failures / high-bytes` rate measured; above ~2.5% the candidate is
dropped, and if it was the model's only pick the pool empties and windows-1252 wins.

Two corrections make the rate trustworthy:

* **Decode under the vendor superset, not the strict base** — real vendor
  extensions (NEC/IBM for Shift_JIS/EUC-JP, HKSCS for Big5) would otherwise count
  as failures and penalize genuine CJK.
* **Discount embedded UTF-8** — mixed-encoding pages (legacy CJK body + UTF-8
  widgets) would otherwise read as 2–9.5% failure.  The validator *skips*
  positions that begin a valid UTF-8 sequence rather than physically stripping
  them, which would misalign a pure legacy-CJK stream and manufacture failures.
  Post-discount, real CJK is ≤1.6% and genuine false-CJK ≥5.3%, so ~2.5%
  separates them.

The veto catches *structurally illegal* false-CJK only.  The *legal-but-wrong*
class — Latin/Cyrillic bytes that form a valid CJK decode at ~0 failures — is the
typicality layer's job (<<junk-filter>>).

[[junk-filter]]
== JunkFilterEncodingDetector — text-quality arbitration

`JunkFilterEncodingDetector` is a `MetaEncodingDetector` backed by the pairwise head of the
bundled `HashedJunkModel`, which was trained on pairs of a correct and a wrong decode of the
same bytes.  Its presence switches the composite into collect-all mode.

[IMPORTANT]
====
*JunkFilter arbitrates over ALL candidate tiers, including DECLARATIVE.*
Real-world web declarations are unreliable, so a `<meta charset>` tag is one
input among several.

A declared charset wins when its decoding is byte-identical to at least one other
candidate's: text quality cannot distinguish the two, so honouring the
declaration ensures downstream divergent bytes (0xA4 = € in ISO-8859-15, ¤ in
windows-1252) decode as the author intended.

For plain first-match-wins, omit JunkFilter — see <<opting-out-of-arbitration>>.
====

=== Arbitration outline

. **One unique candidate** — abstain; composite default ordering wins.
. **Candidate band** — every DECLARATIVE and STRUCTURAL anchor, plus the top two STATISTICAL
  candidates and any other STATISTICAL candidate at confidence 0.5 or more.
. **Decode and clean** — each candidate's decode of the probe (vendor supersets for CJK), then
  `HtmlContentCleaner`: tags stripped, character references expanded as a browser does.
. **Declarative-equivalent-decode preference** — a DECLARATIVE candidate whose decode equals
  another candidate's wins, unless a STRUCTURAL proof (valid wide UTF-8, a BOM, ISO-2022)
  contradicts it.
. **All decodings identical, no DECLARATIVE** — abstain.
. **Hashed arbitration** (`HashedArbitration`) — the decode with the highest pairwise value is
  the champion.  When its pairwise logit over the best decode with different text is below the
  model's deferral threshold, the STRUCTURAL anchor wins, else the DECLARATIVE one, else the
  champion.  The trainer chooses the threshold per model by cross-fit on gold train pages.

`JunkFilterEncodingDetector.candidates()` reports the band, the cleaned decodes, the anchors and
the deciding rule for a stream; the trainer builds its real-decision pairs from it, so training
and detection see the same candidates.

=== Model scoring

The pairwise value of a decode is the sum of its n-gram weights: text normalized (width forms
folded, NFC), whitespace and digits folded, codepoint 1–3-grams hashed into 2^21 buckets.  The
model is linear and has no per-script tables or calibration, so decodes in different scripts
(windows-1251 Cyrillic against GB18030 Han) compare directly.  The pairwise logit divides the
difference of two values by the number of n-grams the decodes do not share: it is the model's
average opinion per differing n-gram, not the amount of evidence.

See xref:advanced/junk-detection.adoc[Text Quality Scoring] for the scorer's own
API and xref:advanced/junk-detection-build.adoc[Building the Junk Detector] for
its model.

=== Why HTML stripping is essential

The score is byte-weighted.  An unstripped HTML probe with 10 KB of whitespace
and tags plus 24 bytes of body gives the body a weight of ~0.0024 — invisible.
Stripping gets the probe to a content-only byte budget where scripts compete on
comparable footing.

`HtmlByteStripper` operates on raw bytes, since ASCII tag delimiters survive
every charset Tika cares about.

[[opting-out-of-arbitration]]
=== Opting out — first-match-wins

This is *not* the default chain.  Omitting `JunkFilterEncodingDetector` puts the
composite detector in plain first-match-wins mode, taking each base detector's
top result in registration order:

[source,json]
----
{
  "encoding-detectors": [
    { "bom-detector": {} },
    { "metadata-charset-detector": {} },
    { "standard-html-encoding-detector": {} },
    { "mojibuster-encoding-detector": {} }
  ]
}
----

BOM, metadata, and meta-tag declarations are then authoritative when present, and
Mojibuster runs only when no declaration fires.  The trade-off: lying declarations
propagate unfiltered, and Mojibuster's top statistical guess is taken with no
text-quality cross-check.

== Accuracy and latency

The model was selected on held-out Common Crawl pages and Wikipedia text and
replaces the byte-bigram Naive Bayes model of 4.0–4.2, with UTF-16 and UTF-32
folded in rather than handled by a separate specialist.  In those selection
runs it was more accurate than the Naive Bayes model across the board, by the
widest margin on non-HTML text.  The model's provenance record
(`hashed-ngram.hng.provenance` next to the model) names the data and gold
version it was trained and selected on.

The scorer visits only windows around non-ASCII bytes and stops early on long
probes (above).  On a laptop core a full detection takes about 0.07 ms for a
1 KB probe of dense non-ASCII text and 0.2 to 1.4 ms for 16 to 64 KB, at most
about 1.5 times the Naive Bayes model's, and less than it on mostly-ASCII text.  Probes whose top two classes stay close (Greek
ISO-8859-7 against windows-1253, EBCDIC variants) are scored in full and are
the slowest.

IMPORTANT: No accuracy figures are published here.  Run `EvalCharsetDetectors`
(below) to measure the current model on your own data.

Earlier ablation runs of the Naive Bayes model are preserved under
`tika-encoding-detectors/tika-encoding-detector-mojibuster/docs/performance/`.

== Model format and training

The model (`hashed-ngram.hng`, format HNG2) is trained outside the Tika
repository and exported to int8 embedding tables plus float dense layers.  The
format, the provenance record, the parity fixture and the steps for replacing
the model are documented in `tika-ml/tika-ml-chardetect/README.md`.  There is
one bundled model and no option to load another.

[source,bash]
----
# Evaluate the bundled pipeline against ICU4J and juniversalchardet
./mvnw clean package -pl tika-ml/tika-ml-chardetect -am -Ptrain -DskipTests
java -jar tika-ml/tika-ml-chardetect/target/tika-ml-chardetect-*-tools.jar \
  --data <corpus>/charset-detect/devtest \
  --lengths 8,32,128,full
----
