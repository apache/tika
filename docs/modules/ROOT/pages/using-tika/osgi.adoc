= Using Tika in OSGi
:toc:

Tika ships two OSGi bundles:

* `tika-core`: the API, the MIME type registry and the default detectors.
* `tika-bundle-standard`: the standard parsers, with the Tika modules and the libraries
  that are not OSGi bundles themselves embedded inside it.

Libraries that already ship as OSGi bundles are not embedded. Deploy them alongside the two
Tika bundles so they can be shared with the rest of your container and updated on their own.

Tika also logs through SLF4J 2.x, so the container needs `org.slf4j` packages and a logging
backend.

The authoritative list is the one Tika's own OSGi integration tests install:
link:https://github.com/apache/tika/blob/main/tika-bundles/tika-bundle-standard/test-bundles.xml[`test-bundles.xml`].
Use the versions that Tika release depends on (`mvn dependency:list` on
`tika-bundle-standard` prints them); later minor versions of the same major also resolve.

If one of these bundles is missing, `tika-bundle-standard` does not resolve, and the
container's error names the missing package.

== Services

When it starts, `tika-bundle-standard` registers:

* a `Parser` service (a `DefaultParser` over all the standard parsers)
* a `Detector` service (a `DefaultDetector` over all the standard detectors)
* its `EncodingDetector`, `LanguageDetector` and `MetadataFilter` providers, which `tika-core`
  merges into its own defaults, so charset detection matches a classpath deployment

No Service Loader Mediator (such as Apache Aries SPI Fly) is needed.

== Tested containers

Every build runs Tika's OSGi integration tests on Apache Felix and Eclipse Equinox. They
check that both bundles resolve, that `tika-core` resolves on its own, and that detection and
parsing through the registered services match a classpath deployment. If you run Tika in
another container, such as Apache Karaf or an Eclipse p2 installation, reports on the
https://issues.apache.org/jira/projects/TIKA[Tika issue tracker] are very welcome.
